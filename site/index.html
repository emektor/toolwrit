Your agent can do exactly what you wrote down.

Not what it was told in a prompt. Not what it can be talked into. What the policy file says.

A writ is a written order from an authority; the return of the writ is the record of what was done under it. The policy file is the order. The audit chain is the return.

The problem

An agent has whatever authority its tools have.

You gave it a filesystem tool so it could read your source. Now it can read .env. You gave it HTTP so it could call your API. Now it can call anyone's.

The usual answer is to write the boundary into the prompt. That is advisory. The model usually complies, sometimes doesn't, and can be argued out of it by a web page it was asked to summarise.

The other usual answer is a second model that judges the first. That is a guess with latency, and a guess you cannot replay six months later when someone asks what happened.

Toolwrit moves the decision out of the model entirely. A YAML policy says which tools may be called and with what arguments. Every call is checked before it executes. Anything not written down is denied.

The policy

Twelve lines is a real policy.

Tools are matched by glob, arguments by constraint. A rule that targets a tool but rejects its arguments doesn't quietly pass — the call falls through to the default, which is deny.

An unknown field is a load-time error, not a shrug. In a security policy a silent typo is how a scope stops being a scope.

version: "1"
default: deny

budget:
  calls: 200
  usd: 5.00
  bytes: 50000000     # data tools may return

rules:
  - id: scoped-write
    tools: ["fs.write"]
    effect: allow
    when:
      path:
        startsWith: ["./src/"]
        excludes: [".."]
How a call is judged
  1. Budget. An exhausted ceiling denies everything, whatever the rules say.
  2. Rate limit. A matching rule whose allowance is spent denies.
  3. Deny beats ask beats allow, among the rules that match.
  4. Default. No match at all falls through to deny, unless you said otherwise.

The same policy, call and ledger state always produce the same verdict — which is what makes a decision replayable from the log rather than merely recorded in it.

Capacity

Exfiltration isn't a forbidden action. It's a permitted one, repeated.

Every read passes the allowlist. The thousandth read passes it too. Only the running total gives it away, so budgets cover calls, tokens, spend, wall-clock — and bytes returned by tools.

A run declares its envelope up front and a human approves it once. Then silence, until a threshold.

plan approved: nightly CRM sync · ergin · bytes 1 000

  warning  bytes at 50%    546 / 1 000
  warning  bytes at 90%    936 / 1 000
  stopped  on read 14      data budget exhausted:
                                1 014 / 1 000 bytes

13 records read. The 14th never ran.

Approve once, hear nothing until 50%. A threshold people mute is the same as no threshold at all.

Evidence

A log that can be checked, not just kept.

Every decision is appended to a hash chain. Edit an entry and every hash after it stops matching.

But a chain alone cannot catch a truncated log — a prefix of a valid chain is itself a valid chain, and verifies clean. An agent that deletes its last twenty entries hands you a file that passes.

So the receipt goes somewhere the agent can't reach, and you check against that.

$ toolwrit verify truncated.jsonl
ok: 5 entries verified
exit 0                        ← the deletion is invisible

$ toolwrit verify truncated.jsonl --against anchor.jsonl
FAILED: anchor check
  chain head d08543517b60 does not match the
  receipt's head 168b70717625
  (5 entries present, receipt recorded 10)
exit 1

Tamper-evident, not tamper-proof. Anchor the head somewhere the agent cannot rewrite, or this proves nothing — Toolwrit can make that one command, it cannot make it true for you.

Both languages, one chain

Your agents are Python. Your platform is TypeScript.

Both implementations produce the same canonical form, so a log written by one verifies with the other and the entry hashes are equal. (The files can differ cosmetically in field order; the hashes cannot.)

A CI job checks it on every commit, because nothing else would stop the two from drifting apart in silence.

What it is not

The limits, before you find them.

A security control that is oversold is worse than none, because it displaces the control you actually needed.

  • It governs the tool boundary. It does not read prompts or model output.
  • A bytes ceiling bounds a run at the limit plus one call — a result's size cannot be known before the tool runs.
  • The audit log is tamper-evident, not tamper-proof. Unanchored, an attacker with write access can rewrite the whole chain.
  • It is not a network egress filter, and it cannot stop an allowed tool from doing something unwise within policy.
  • It cannot survive its own host being compromised. The sidecar must run outside the agent's blast radius.
  • Under the MCP proxy, token budgets need the host application to report usage — MCP responses carry no token accounting.
